# Changelog

Every StoryForgeAI release, newest first. The five most recent also appear in
the [README](README.md#update-log); this file is the complete record and nothing
is ever removed from it.

The version shown in the app's footer is the top entry here.

| Version | Date | What changed |
| --- | --- | --- |
| **1.32** | 2026-08-08 | **Reference mode's clip estimates halved, because the renders did.** The figures shown beside the two MiniMax H3 options came from a run of measurements on WanGP v12.42, which predicted about 29 minutes for a clip holding one character. The same clip on v12.432 takes **15:26**, or **12:35** with Spectrum step skipping enabled for the model in WanGP. The shape of the cost is unchanged — a fixed amount plus a cost for each reference image — so the numbers are that series re-based rather than re-guessed, and the settings screen still names the machine they were measured on. An estimate that is nearly twice the real figure is its own kind of wrong: it talks people out of a tier that is affordable. |
| **1.31** | 2026-08-08 | **A spoken line with its delivery described is now marked as speech.** MiniMax H3 only utters what is inside its speech markup — a quoted sentence outside it is description, and the clip shows someone talking in silence. The markup was applied only where the quotation followed the verb immediately, so `says, "New stakes."` was caught and `says in a steady, commanding voice, "New stakes."` was not — and writing the delivery is exactly what the guidance asks for, so the better the prompt the more likely the line was lost. A clause between the verb and the quotation is now allowed, and kept beside the verb rather than swept inside the markup, since the guide is explicit that only the words themselves are uttered. |
| **1.30** | 2026-08-08 | **A scene continuing from the one before it is now handed its actual opening frame, not just told about it.** 1.29 said the fix for a carried-over frame in reference mode was to stop carrying frames over. That was wrong, and worse than the problem — cutting removes the continuity the setting exists to provide. The frame is not the mistake: a scene that ends on one character and continues into a shot of another should *open on the first and move to the second*, which is a perfectly good continuous take. What was missing is that the clip prompt is written from a scene card describing where the shot was meant to *end up*, and a single instruction in the system prompt could not outweigh it. The previous scene's closing frame is now part of the material the agent writes from, stated as this clip's first image, so the shot is written as the move from there. The continuity setting says this rather than recommending a cut. |
| **1.29** | 2026-08-08 | **Says why carrying a frame forward does not work in reference mode.** Every other video model takes its start frame *positionally*: the picture is pinned to the opening moment and the model builds outward from it, so a clip prompt describing a slightly different opening is a wrinkle rather than a problem. Reference mode has no positional input at all — the opening is whatever the prose says it is. So a scene that inherits its start frame is being handed a picture of one thing while describing another, and the words win every time: the clip opens on a shot that was never rendered. Telling the writing agent about the inherited frame helped and did not settle it, because the scene card itself describes the opening the storyboard intended. The continuity setting now says this plainly when reference mode is selected, and points at **Cut**, where each scene renders the opening its own prompt describes and the two finally agree. |
| **1.28** | 2026-08-08 | **A scene that opens on the previous scene's last frame is now written that way.** Where a project carries end frames forward, a scene's clip does not begin on its own start-frame prompt — it begins on the picture the scene before it ended with. Nothing told the prompt agent that, so it wrote an opening from the frame it *expected*, and the two described different shots: one clip was told to hold a picture of a woman leaning over a table while its own prose opened on a close-up of a man reading cards. Both cannot be first, and the words win. The agent is now given the previous scene's closing frame and told to begin at what it already shows, writing only what changes from there. Also fixed: substituting a character's reference label into the prose was reaching the clauses appended after it, turning "the frame is free of … muscular Tracey" into an instruction to leave the subject out of the shot entirely. |
| **1.27** | 2026-08-08 | **Corrects what the last release said about step skipping.** 1.26 stopped StoryForgeAI switching on WanGP's step-skipping cache, and explained that as being unable to control how hard it skips — pointing at a strength setting that was being ignored. That setting is not Spectrum's: Spectrum offers only a start percentage, and the strength belongs to a different cache type entirely, so the value was inert and the explanation was wrong. Leaving the cache alone is still right, for a better reason: it is chosen per model in WanGP's own UI and arrives with that model's saved settings, so a model configured for Spectrum already gets it. The settings screen now says that rather than the wrong thing, and no longer implies the app is working around WanGP. |
| **1.26** | 2026-08-08 | **Reference mode stopped switching on a speed-up whose strength it cannot set.** WanGP's step-skipping cache is worth about a third of the render time when it runs at the right strength — and StoryForgeAI cannot set that strength. The value it submits is discarded and WanGP uses its own saved figure, which on this machine was more than twenty times too aggressive: the denoising was largely skipped, the clip stopped following its prompt, and it finished in nine minutes rather than twenty. That was the cause of a render that ignored its opening frame, and of an earlier one that came back as a Japanese cartoon. The cache is now left entirely to WanGP. Clip estimates go up accordingly, and the settings screen says what the speed-up is worth and where to turn it on — in the WanGP UI, where its strength can actually be chosen. |
| **1.25** | 2026-08-08 | **Reference mode now describes the opening frame it is actually sent.** Where a project carries end frames forward, a scene's start frame *is the previous scene's end frame* — its own start-frame prompt describes a picture that was never rendered. Reference mode tells the model what its opening frame contains, and it was reading that from the prompt rather than the picture, so from the second scene onwards it described the wrong shot entirely: one scene was told its opening was a medium close-up of a man when the frame supplied was a wide group shot. The model builds what the words say, so the clip opened on something nobody had supplied. The description now comes from whichever frame is really being sent. Also fixed alongside it: that description was taken from the first sentence of a keyframe prompt, and keyframe prompts are required to open with shot size and camera height — so it was reliably "medium close-up, eye level, 35mm lens" and reliably said nothing about what was in the shot. |
| **1.24** | 2026-08-08 | **A pinned character's photograph is now tied to the person in the shot.** Reference mode hands the model a photograph and a numbered label for it, but the clip prompt calls people by name — the writing agent has no idea a photograph exists — so nothing connected the two. A reference with nothing holding it does not simply get ignored: a live run put copies of the referenced face on several different people around a table. Where the prose names a character who has a photograph, it now carries that character's label, exactly as a hand-made render that held identity for a full clip does. Spoken lines are stepped over, since a name inside dialogue is said aloud and a label there would be read out as written. |
| **1.23** | 2026-08-08 | **Rewriting a scene's prompts is now recorded as having happened.** It never was: the rewrite replaced the wording and left the scene carrying the provenance of whatever run first wrote it, so the badge on the card described prompts that no longer existed, and the new staleness warning could never clear — rewriting every scene changed nothing it could see, so it went on telling you the prompts were out of date. Both the single-scene rewrite and the whole-storyboard one now commit their provenance alongside the prompts they produced, the way generating a storyboard always has. |
| **1.22** | 2026-08-08 | **Rewriting every scene's prompts no longer depends on the app warning you first.** The button only existed inside the amber staleness banner, so when the banner was correctly silent — nothing about the project had changed — there was no way to run it at all, short of visiting every scene card in turn. **Rewrite all prompts** now sits with the other batch controls, where it is also the right tool after editing scene cards or changing the cast. The banner itself now catches a second kind of stale: prompts are tagged with the version of the guidance that wrote them, so an update that changes what the agents are told is noticed the same way a change of model is. Previously that was invisible — the prompts matched the pinned model perfectly and were still written to instructions two releases old. |
| **1.21** | 2026-08-08 | **Reference mode's clip prompt stopped competing with its own opening frame.** The prompt named the first frame and then, a sentence later, described the opening again in the writing agent's own words — and those words are what the model built, because prose beats a picture it has only been told about. Two changes, both aimed at the same sentence: the frame's own description now sits immediately before the agent's prose rather than only in the bookkeeping above it, followed by an explicit statement that nothing happens before the first change; and the agent is now told not to describe the opening composition at all in reference mode, but to open at the state its own start-frame prompt describes and let the first thing it writes be the first thing that moves. A clip prompt is written to stand alone, which is right for every other model and exactly wrong for this one. |
| **1.20** | 2026-08-07 | **Reference mode now says what its two keyframes contain, and stops contradicting them.** The prompt told the model which picture was the opening frame but never what was in it — so "match this" had nothing to match against, and clips kept opening on an invented shot. Each anchor is now described from the prompt its keyframe was rendered from, the way a hand-made render that came out correct describes them. The second half is subtler and was working against the first: a clip prompt describes the scene from the beginning, and its opening sentences can disagree with the frame that was actually rendered — one scene's keyframe showed a robot with its head already tilted while the clip prompt had it standing still and tilting later. Prose beats a picture the model has only been told about, so the shot is now instructed to hold the subject's exact pose in that frame as well as its framing and light. |
| **1.19** | 2026-08-07 | **Reference mode now says which picture the shot opens on, in the place that decides it.** Reference mode has no positional keyframes — the model knows a picture is the opening frame only because the prompt says so — and the prompt was saying it only in the bookkeeping sections at the top. The result was a clip that reached its closing frame exactly and opened on something invented. The shot description itself now begins by naming the opening frame and ends by naming the closing one, the summary states which picture the shot runs from and to, and each retention line says at which end it applies. That is four statements of the same fact, matching a hand-made render of the same model that came out correct — the description is the one that cannot be left out, because the writing agent is describing a scene rather than a set of pictures and will never mention them on its own. |
| **1.18** | 2026-08-07 | **Reference mode now sends the settings a working render actually used.** Three of them were wrong, and together they produced clips with nothing to do with their prompt — in one case a Japanese cartoon, complete with Japanese speech. The step-skipping cache was switched on beside a *strength* left over from WanGP's saved state, and at that value it skipped so much of the denoising that the model abandoned the prompt and fell back on whatever it was trained on; it now carries the strength measured alongside it, which is the difference between a clean 20-minute clip and an 8-minute one that is unusable. The reference images were labelled with the wrong letter, so the model took the wrong picture as its opening frame and the supplied start frame surfaced at the end. And a prompt written in labelled sections was being split into a separate prompt per section, because a carriage return meant something to WanGP that it did not mean to us. All three were settled by reading the settings WanGP writes beside every clip it renders — the app's own guesses had been wrong in both directions. |
| **1.17** | 2026-08-07 | **Reference mode stopped being told which picture is which in a language it does not speak.** WanGP labels reference images with letters — people, or a scene followed by people — and StoryForgeAI wrote that label on every job carrying references, because the models it had met until now ignore the images without it. MiniMax H3's reference variant is not one of those: it ships that field empty and reads the pictures straight, so writing a label changed which one it took as the opening frame. The result was a clip whose supplied start frame turned up at the *end* and whose opening was invented from nothing. That field is now left as the model ships it wherever a model publishes no default of its own, which is exactly the configuration the Wan2GP UI uses when the same job is set up by hand. |
| **1.16** | 2026-08-07 | **A failed scene now says why, on the screen.** The reason a batch failed was only ever in the tooltip of a small red chip, which is where an error goes to be missed — a scene could fail and the honest answer to "why?" was "hover over it". Failures are now listed in full under the batch controls. The message they carry is better too: a model that accepts no LoRAs used to say only that, and now names the LoRAs in question and where to clear them. That case has one common cause, so it is also headed off earlier — selecting reference mode with video LoRAs still chosen warns on the settings screen that every clip will fail, rather than letting you find out after the render. Reference mode takes no LoRAs at all, and accelerators are actively harmful there: a 4-step LoRA finished in a quarter of the time and scattered the referenced face across several people. |
| **1.15** | 2026-08-07 | **Clip prompts stopped narrating their own instructions.** Every video prompt was asked for "one dominant action and at most one secondary movement" — and models handed that phrasing back in the prose, writing *"the robot performs its dominant action: it tilts its head"*. A video model renders those words rather than obeying them, so the instruction ended up described in the picture and spent part of a prompt budget that is already tight. The same shape is now asked for by describing it rather than naming it, and every prompt is told to write only the scene — never to restate the brief or announce what a sentence is about to do. The scene card also warns when a model narrates the brief anyway, alongside the existing checks for repeated sentences and dropped dialogue. |
| **1.14** | 2026-08-07 | **Reference mode's prompts are now written for reference mode.** Both MiniMax H3 variants were being given the same instruction — one that says the two keyframes are pinned to the opening and closing moments, so write the path between them and not the endpoints. That is true of first-and-last-frame and false of reference mode, which has no positional input at all: every picture arrives as a numbered reference and the model knows what one *is* only because the prose says so. Prompts were being written for conditioning that never arrives, leaving both endpoints stated by nothing. Reference mode now gets its own instruction — describe the whole shot including how it opens and closes, and name and describe each character, because that description is what binds a photograph to a person rather than to whoever the model picks. The scene card also now says what generation adds: the labelled structure and the reference lines are built at render time from the cast, so the box holds the prose and not the whole message. |
| **1.13** | 2026-08-07 | **Say when the prompts were written for a video model the project no longer uses — and rewrite them all in one click.** Clip prompts are written for a specific model family: LTX asks for four to eight sentences, MiniMax H3 for 350 to 500 words with its own camera vocabulary and the soundtrack split into separate layers. Change the pinned video model after the storyboard exists and every prompt is still phrased for the old one — which fails silently, because the clip renders perfectly well and is merely worse than it should be, with nothing on screen to say why. Prompts now record the family they were written for, and the Storyboard screen warns when that no longer matches, naming both. A storyboard written before that record existed is not left out: whether a prompt carries a separate soundscape or score is asked for by one model family and no other, so the app can tell what wrote it and says so as a maybe rather than a certainty. Each scene is judged on its own and the count is reported — a storyboard rewritten halfway, or one whose run failed partway through, would otherwise pass on the strength of its best scene. **Rewrite all scenes' prompts** re-runs the two prompt agents across the whole storyboard against the models pinned now; previously this could only be done one scene at a time, which is how half a piece ends up rendered with the wrong prompts. Scene cards, the story and the shot list are untouched. |
| **1.12** | 2026-08-07 | **The MiniMax H3 choice only appears when H3 is the pinned model, and its timings now say whose machine they came from.** The reference-versus-keyframe choice was offered whenever an H3 checkpoint existed anywhere in WanGP's catalogue, so a project rendering on LTX-2 was shown a control that had nothing to do with it — and could sit displaying a selection its own model would never honour. It now appears only when the pinned video model is H3. The render times quoted beside each option were measured on one workstation and read as though they were universal; they now name it (Intel Core 9, 64 GB RAM, RTX 5070 Ti 16 GB) and say plainly that the ratio between the options is the part that carries to other hardware. |
| **1.11** | 2026-08-07 | **Say which model "Automatic" is actually using, and why a model list is empty.** Leaving a model on **Automatic (best ranked)** gave no clue what would render — the ranking is real, but it is invisible, so there was no way to tell a sensible default from a wrong one. Both pickers now name the model a render would resolve to, resolved through the same code the renderer uses rather than a second guess at it, and accounting for the substitution that happens when pinned characters need a model that accepts reference images. Separately, an empty picker used to read "0 of 0 shown" whether WanGP had no such models or was not running at all — two very different problems that look identical from the catalogue. The screen now says which it is, and names the address it tried. |
| **1.10** | 2026-08-07 | **Hold a character's face for the whole clip, not just at its two ends.** A clip built from a start and an end frame can let a character deform through the middle of the shot and arrive correct again at the finish, and face-swapping the keyframes cannot touch it — the keyframes were never the problem. Where MiniMax H3's **reference** checkpoint is installed, project settings now offers it as a second way of giving H3 the shot: the two frames go in as references rather than anchors, alongside one photograph of each character present, and the likeness holds for the full clip. A live 13.7-second run held identity throughout and lip-synced its dialogue. It is a deliberate choice, not a default, because it costs about three times as much time — the screen states the estimate for your cast before you pick it — and caps clips at 14 seconds, this variant having no stitching to render past that. It refuses rather than degrades: one keyframe instead of two is refused, since a single anchor was measured losing the composition entirely, and a fourth character in a scene is reported rather than quietly dropped. |
| **1.09** | 2026-08-07 | **Accelerator LoRAs named with underscores now run at the step count they were built for.** A LoRA whose filename says how many steps it needs — `4step`, `8_steps` — has that number read off it, because running a distilled LoRA at the model's full count throws away the time it exists to save. The pattern only matched when the count was set off by a dash or a space, so MiniMax H3's `minimax_h3_turbo_4step` was missed and its clips ran at twenty steps instead of four: **five times the wait**, for a picture the LoRA was never tuned to produce. Any accelerator whose filename separates the count with an underscore was affected. |
| **1.08** | 2026-08-06 | **A permanent changelog, and MiniMax H3's own prompt format behind a flag.** The update log below only ever shows five releases, so everything older used to fall off the end and vanish; [CHANGELOG.md](CHANGELOG.md) now keeps every release ever made, and the release checks refuse to drop a row from the README unless it is already recorded there word for word. Separately, `H3_NATIVE_PROMPT_FORMAT` sends H3 the labelled structure MiniMax publishes rather than one paragraph of prose. It stays **off**: three live A/B pairs each showed the labelled arm producing no spoken dialogue at all, where plain prose said the line correctly every time. What the testing fixed along the way, and what everyone gets: H3 writes its own soundtrack and was being given no audio direction at all, so it invented one and **sang a line the scene had only asked it to say** — ambience and score now always reach it; and clip prompts for H3 are now written at the length MiniMax ask for rather than a third of it. Also fixed: the cap that holds H3 at 480p for upscaling was being reported and then discarded whenever a caller passed no frame settings. Every path in the app passes them, so no render was affected — but the log was claiming a clamp the job would not have got. |
| **1.07** | 2026-08-06 | **MiniMax H3 prompting corrected against MiniMax's own guide, plus two fixes found while checking it.** A live schema dump showed H3 declares no negative prompt at all, so every exclusion written for an H3 clip — flicker, identity drift, the terms your pinned characters contribute — was being discarded on the way to the renderer; those now travel inside the prompt as the thing to show instead, the way they already did for FLUX. The single-pass clip length was also wrong: H3 renders about **15 seconds** in one pass, not the 20 the settings screen claimed, so a 20-second clip was being stitched from overlapping passes without saying so. Pinning an H3 **Ref2VA** model is now refused rather than quietly dropping both keyframes and rendering from the prompt alone — FL2VA is the variant that takes a start and end frame. The prompt guidance itself now follows MiniMax's published camera vocabulary and keeps ambience, audience-only score and speech as the three separate layers H3 expects. |
| **1.06** | 2026-08-06 | **Replaced frames now actually appear on the storyboard.** A frame swapped in place — an imported image, a face swap, the carried-over start frame that goes with it — kept the same media address, so nothing told the browser the picture behind it had changed and the scene went on showing the old one. The record was right and the screen was wrong, which is the worst way for it to be wrong. Each image and clip is now addressed by its content, so a replacement is visible as soon as the card reloads. The scene card also stops claiming the following scene was updated unless it can see that it was. |
| **1.05** | 2026-08-06 | **Import a keyframe instead of rendering one.** Sometimes the picture already exists — a photograph, or StoryForge's own render taken away and edited — and no amount of re-rolling a seed will get the model back to it. Each scene card now takes an image for its start or end frame, and everything downstream reads it: the end-frame reference, the clip, and the next scene's carried-over start frame, which is replaced along with it where the project carries end frames forward. The card says what the import costs: the pinned seed no longer describes that frame, and **Regenerate media** re-renders both frames and throws the image away — **Regenerate video for selected scenes** rebuilds the clip and keeps it. |
| **1.04** | 2026-08-05 | **MiniMax H3 support, and a fix for every video model.** H3 was unrecognised, so its clips were prompted with no guidance at all and nothing was written for the soundtrack it generates from the same prompt — it now gets both. Keyframe and clip resolution are separate settings, since a slow video model is no reason to render the frames that fix identity and wardrobe small; H3 is held at 480p and asks WanGP for the upscale rather than inheriting whatever was last selected there. Clip length is editable after creation and names the length past which a model stitches a clip from overlapping passes. Affecting every project: clip length was being sent to WanGP as an audio setting the model meant something else by. |
| **1.03** | 2026-08-05 | **Copy the previous scene's LoRAs.** Setting the same override on a run of scenes meant picking every LoRA again on each card. Where the preceding scene has its own selection, its LoRA panel now offers **Copy previous scene's LoRAs**, which fills in both the image and video lists so you can save them as they are or adjust first. It is a one-time copy — later edits to the earlier scene leave this one alone. |
| **1.02** | 2026-08-04 | **Per-scene end-frame reference override.** A carried-over start frame is handed to the end-frame render as a reference image, which holds wardrobe and location across the seam — but holds props too, so an action meant to put a glass down left it in shot. **Match the carried-over frame** on the scene card turns it off for that scene alone. Also: corrected the README's claim that clips are a fixed 20 seconds, and added this log. |
| **1.01** | 2026-08-04 | **Live batch progress.** A phased run banks each scene's keyframes as it renders them instead of at the end of the phase, so the storyboard fills in while the batch is still going and cancelling no longer discards hours of finished frames. Per-scene chips now name the phase, the counter reports renders that succeeded with failures listed apart from them, and the clip phase stops calling itself that in a keyframes-only project. |
| **1.00** | 2026-08-03 | Baseline release: the agent crew, storyboard, WanGP media generation, character library and wardrobe timeline, LoRA selection, assembly and export, provenance, durable tasks, and the accessibility pass. |
